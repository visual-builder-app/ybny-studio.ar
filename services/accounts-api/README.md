# خدمة يبني للحسابات والصلاحيات (accounts-api)

## الحالة والحدود

خدمة **Express/TypeScript** تُشغَّل محلياً داخل Docker فقط، وهي الواجهة الوحيدة المسموح لها بالاستعلام من دالة قاعدة الحسابات `accounts_api.get_access`. لا تتصل بقاعدة مشاريع Webstudio، ولا تُنشر على أي استضافة، ولا تصدر حتى الآن تصاريح مستخدمين.

**منفّذ ومُختبر محلياً:**

- حرس مصادقة على كل مسارات `/api`: تتطلب ترويسة `Authorization: Bearer <service-token>` مع مقارنة بزمن ثابت. طلب بلا رمز أو برمز خاطئ يعيد `401` قبل لمس قاعدة البيانات.
- تحقق مدخلات: `memberId` بصيغة UUID و`environment` إحدى `test` أو `live`، وما دون ذلك `400`.
- استعلام الصلاحية عبر دالة قاعدة البيانات فقط (لا قراءة مباشرة لجداول الأعضاء أو المدفوعات)، والرد يحتوي المنتج وتاريخ انتهائه:

```json
{ "hasAccess": true, "products": [ { "productKey": "ybny.studio.pro", "expiresAt": "2026-09-21T12:00:00.000Z" } ] }
```

`expiresAt` جزء من العقد: الخدمة المستدعية تحتاج تاريخ الانتهاء لتحديد مدة أي تخزين مؤقت للصلاحية بدلاً من تخزينها بلا حد. عند غياب الصلاحية يكون الرد `{ "hasAccess": false, "products": [] }`.
- حماية العملية: مهلات اتصال واستعلام (5 و15 ثانية)، ومنفذ خطأ لمجمّع الاتصالات حتى لا يُسقط انقطاع قاعدة البيانات العملية، وأي خطأ يعيد `500` بصيغة JSON بدل صفحة HTML.
- أسرار من **ملفات** لا متغيرات بيئة: `database-url` و`service-token` بصلاحيات `0600` في مجلد خاص بالمستخدم خارج المستودع، ويُمنع احتواء بيئة الحاوية على أسرار.
- الحاوية على شبكتين: `edge` (bridge عادي) لتسمح بنشر المنفذ على `127.0.0.1` فقط، و`private` (internal) للوصول إلى قاعدة الحسابات. تشغيل الحاوية على شبكة `internal` وحدها يمنع وصول المضيف إليها فعلياً، وهو سبب عطل الاتصال السابق.
- 11 اختبار سياسة ووحدة بلا Docker (شبكة ومنافذ وحماية الحاوية، أسرار ملفات بصلاحيات 0600، بناء رابط قاعدة البيانات من دور الصلاحيات وحده، فشل مغلق عند غياب الاعتماد)، و6 اختبارات قبول من الطرف إلى الطرف على قاعدة PostgreSQL حقيقية: صحة عامة، رفض بلا رمز، رفض برمز خاطئ، تحقق من الجسم، عضو غير موجود (مع التأكد أنه كان مرفوضاً قبل وجود الاشتراك)، واشتراك حالي فعلي (مع `expiresAt` ورفض بيئة `live` وحساب موقوف)، وحذف عضو الاختبار في `finally`. غياب المتطلبات يُفشل الاختبار ولا يجعله «ناجحاً متجاوزاً».

**غير منفّذ بعد:** مزود هوية وجلسات، إصدار تصاريح للمستخدمين، إدارة اشتراكات، التحقق من توقيع Webhooks الدفع، الربط بـ `ybny.net` أو `ybnyai.com`، تفعيل Server Mode، والاستضافة السحابية والنسخ الاحتياطي. تشغيل هذه الخدمة لا يعني أن الدخول أو الاشتراكات أصبحت جاهزة.

## التشغيل المحلي

المتطلبات: Docker في WSL/Linux، Python 3.10+، وقاعدة الحسابات من `services/accounts-db` قيد التشغيل.

```bash
# قاعدة الحسابات أولاً (مرة واحدة لكل جلسة عمل)
wsl.exe -d Ubuntu-24.04 -- bash -lc 'python3 /mnt/c/Users/HEART/Desktop/ybny-studio.ar/services/accounts-db/runtime.py --sudo start'

# ثم الخدمة: تهيئة الأسرار، بناء الصورة، والتشغيل
wsl.exe -d Ubuntu-24.04 -- bash -lc 'cd /mnt/c/Users/HEART/Desktop/ybny-studio.ar/services/accounts-api && python3 runtime.py --sudo up && python3 runtime.py --sudo status'
```

`provision` يكتب ملفي السر فقط. `status` يعرض حالة الحاوية والمنافذ والشبكات وأسماء ملفات الأسرار، ولا يطبع أي قيمة سرية. `down` يوقف الحاوية ويحفظ الأسرار وقاعدة البيانات.

### اختبارات القبول

```bash
wsl.exe -d Ubuntu-24.04 -- bash -lc 'cd /mnt/c/Users/HEART/Desktop/ybny-studio.ar/services/accounts-api && YBNY_ACCOUNTS_DOCKER_SUDO=1 python3 tests/test_access_end_to_end.py'
```

تنشئ عضواً واشتراكاً مؤقتين بوسم `e2e-` ثم تحذفهما في `finally`؛ تحققنا بعد التشغيل أن جداول الأعضاء والعملاء والاشتراكات والمدفوعات في قاعدة الحسابات الدائمة خالية من صفوف الاختبار.

### استدعاء الخدمة من خدمة أخرى (خادم لخادم)

```bash
curl -s -X POST http://127.0.0.1:4000/api/access \
  -H "Authorization: Bearer $(cat ~/.local/share/ybny-accounts-api/service-token)" \
  -H "Content-Type: application/json" \
  -d '{"memberId":"<uuid>","environment":"test"}'
```

لا يوضع الرمز في المتصفح ولا في كود الواجهة: الاستدعاء من خادم موثوق فقط. تبقى قاعدة الحسابات بلا منافذ منشورة.

## سياسة الأسرار

- المسار الخاص: `~/.local/share/ybny-accounts-api/` بصلاحيات `0700`، وما فيه بصلاحيات `0600` ومملوك للمستخدم نفسه (يفحصه `runtime.py` ويرفض غير ذلك).
- `database-url` يُبنى وقت التشغيل من ملف اعتماد قاعدة الحسابات لدور `ybny_access_service` فقط، ولا يُطبع.
- `service-token` يُنشأ عشوائياً مرة واحدة؛ لحذفه وإعادة توليده أوقف الخدمة، أزل الملف، ثم `provision` و`up`، وحدّث الخدمة المستدعية.
- إن تغيّرت كلمات أدوار قاعدة البيانات، أعد `migrate` من `services/accounts-db` (يعيد ضبطها من ملف الاعتماد الحالي) ثم `provision` و`up` هنا.
- لا تُنسخ هذه الملفات إلى صورة Docker أو مستودع Git أو محادثة. `.gitignore` يستثني `node_modules` و`dist` و`.env`.

## الحدود الأمنية المتبقية

- هذه **خدمة تطوير محلية**، وليست بوابة هوية إنتاجية: لا جلسات مستخدمين، ولا تحديد معدل، ولا TLS، ولا تدوير مفاتيح آلي.
- **لا تصريح لكل عضو ولا تسجيل تدقيق بعد:** الترويسة المشتركة تصادق الخدمة المستدعية فقط، فأي حامل للرمز يمكنه الاستعلام عن أي `memberId`. تعليق مخطط قاعدة الحسابات يوجب تصريح المتصل للعضو المطلوب قبل الإنتاج، وهذا العمل مؤجّل ومقصود.
- الحاوية غير جذرية (`USER node`) بلا قدرات (`cap_drop: ALL`)، بقرص للقراءة فقط، وبحدود موارد، ومنفذها على `127.0.0.1` فقط.
- أي استخدام إنتاجي يحتاج: مزود هوية موثوق، تخزين أسرار مركزي، تدوير مفاتيح، تدقيق على مستوى المستخدم، مراقبة، ونسخاً احتياطية مُختبرة.
- إن ظهرت كلمات مرور التطوير في سجل أدوات أو محادثة، اعتُبرت مكشوفة ويجب تدويرها قبل أي استخدام خارجي.
